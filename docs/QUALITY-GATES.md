# 코드 품질 강제 구조 (3층 모델)

AI가 작성하는 코드의 품질을, **손으로 닦지 않고** 시스템으로 유지하기 위한 구조.
원리: 확률적 생성기(AI)를 결정적 검증기로 감싸, **판정 가능한 속성만** 결정적으로 강제한다.

## 핵심 결정 규칙 — 게이트냐 권고냐

규칙을 하드 게이트로 만들지 소프트 권고로 둘지는 **예외(정당한 위반)의 빈도**로 정한다.

| 예외 빈도 | 처리 | 이유 |
|---|---|---|
| **드묾** | 하드 게이트 (CI 차단) | 오탐 거의 0 → 생산성 저하 없음 |
| **흔함** | 소프트 권고 (표시만) | 오탐 잦으면 무시·우회 → 생산성 저하 |

> allowlist가 커질 것 같으면 = 그 규칙은 하드 게이트 감이 아니다. (예: `now()` 정당성은
> 예외가 흔함 → 하드 게이트 금지, 소프트 권고로.)

## 3층

### 1층 — 예방 (확률적, 가장 값쌈)
AI가 나쁜 패턴을 애초에 덜 쓰게 유도. LLM은 규칙 문서보다 **주변 코드**를 더 잘 모방하므로,
좋은 패턴을 코드베이스에 예시로 까는 것이 가장 강력하다. (`.claude/rules/junho3-code-rules.md` 참고)

### 2층 — 하드 게이트 (결정적, "무조건")
예외가 드문 규칙만. 실패 시 CI가 머지를 차단한다.
- **ArchUnit** (`src/test/java/.../archunit`): 레이어 의존성, 네이밍 접미사,
  `@Transactional(readOnly)` 금지, Custom Repository 사용 금지
- **PMD** (`config/pmd/junho3-ruleset.xml`): 불필요 로컬변수 등. 현재 `ignoreFailures=true`
  (report-only) — 볼륨 확인 후 차단으로 승격 여부 결정
- 실행: `./gradlew test` (ArchUnit), `./gradlew pmdMain` (PMD)

### 3층 — 소프트 권고 (판단 속성)
예외가 흔해 결정적 검사기가 없는 것. **차단하지 않고 사람 주의를 환기**.
- `/junho3-code-review` 슬래시 커맨드가 diff를 판단 규칙(P1~P5)에 대조해 표시
- now() 주입, 단일 사용 alias, 얕은 래퍼, 네이밍 의미, 추상화 정당성

## 왜 이렇게 나누나

- **판정 가능 + 예외 드묾** → 2층. AI가 참조하든 말든 CI가 100% 강제.
- **판정 불가(판단 속성)** → 3층. 어떤 도구로도 결정적으로 못 만든다(의도가 필요).
  소프트 권고 + 사람 판단이 최선이며, 그게 정직한 천장이다.
- 2층은 "무조건", 3층은 "표시 후 사람 결정". 둘을 섞지 않는 것이 생산성을 지키는 핵심.
